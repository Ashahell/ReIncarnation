## Their position (Kalamatee)

- Not reproducible with upstream code: on a pc-x86_64 QEMU guest with
  no HDA, `hdaudio.audio` DriverInit returns FALSE, the library is
  expunged, `OpenDevice("ahi.device",0)` falls back via void.audio.
  Tested with `AddAudioModes REFRESH` and a stock
  CreateMsgPort/CreateIORequest/OpenDevice probe.
- Our symptom (#GP error 0, privilege violation, no CR2) is the
  signature of an aligned SSE store (`movaps`) to a stack local on a
  stack misaligned by 8 — reproducible by calling `OpenDevice` with
  RSP off by 8; the fault lands on the first `movaps` along the path
  (iffparse in one build, hdaudio init in another).
- Asked to check our `startup.o` (main and every function entered with
  RSP%16==8) and, if the crash persists with corrected startup, post
  the alert PC/module/offset + RSP from More.

## Our verification (before replying)

- Direct `movaps`-to-stack-local test (forced emit, verified in
  disasm) runs clean in both process `main` and a `CreateNewProcTags`
  task built with our exact recipe (v1 build-pc `startup.o`,
  `-nostartfiles -no-pie`). Static: the entry body has no `sub %rsp`
  frame and preserves entry alignment at every call. Startup
  exonerated — there is no "corrected startup" to switch to.
- Therefore the fault is driver-side (its own buffers/stack), same
  family as the codec-less-guest HUNK-alignment faults. Note ours is
  **sb128**, not hdaudio: the guest has no HDA at all.

## Follow-up: closed as not-upstream; fork build bug found (2026-09-27)

Upstream withdrew the caller theory (our RSP is aligned), reproduced
clean results with our flags on an upstream guest, and closed the
issue: fixed r12 is our fork's ABI rule, so every module must be
built with `-ffixed-r12` — check the AHI objdir's `config.log`
`CFLAGS=` line. Checked:

- `core-pc-x86_64/.../gen/workbench/devs/AHI/config.log`:
  `CC=clang`, `CFLAGS='... -O2'` with **no `-ffixed-r12`** — exactly
  as predicted. AHI is also the odd one out by compiler (clang vs
  the gcc that carries the fork's `FIXED_REGISTERS` reservation), so
  clang-built drivers use r12 as scratch while the rest of the tree
  treats it as reserved. First cross-library calls happen in
  `DriverInit` — matching "any driver, always in DriverInit".
- The v1 tree's own configure/arch has no `-ffixed-r12` anywhere; the
  reservation lives only in the gcc config patch, which clang never
  reads. Fix location: get the flag into AHI's configure environment
  (`USER_CFLAGS` in `workbench/devs/AHI/mmakefile.src` or the build
  env), rebuild, redeploy `sb128.audio`, re-test the open. That tree
  is another session's lane — handed over, not fixed from here.
- Not proven end-to-end (would need an AHI rebuild in their tree);
  reported as mechanism-confirmed, fix-proposed.

> **Status: Disputed (2026-09-28).** The r12 mechanism above was never
> proven end-to-end. The fix that did work end-to-end
> (`2026-09-28-audio-in-qemu.md`) was rebuilding the drivers without
> auto-vectorization (`-fno-vectorize -fno-slp-vectorize`, per-TU
> `-mno-sse`). Each rebuild moved the fault exactly one site up the
> ladder: sb128 `DriverInit+0x135` → hdaudio `card_init` → `ahi.device
> ReadConfig`. That is the same misaligned `movaps` on HUNK-shifted data
> every time (see `160d1f3`: movaps at +0x135). The missing
> `-ffixed-r12` in AHI's clang `config.log` is still true and still worth
> fixing, but the evidence points to vector alignment as the fault that
> actually fired.
