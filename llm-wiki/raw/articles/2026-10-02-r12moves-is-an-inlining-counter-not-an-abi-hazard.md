# `r12moves` is an inlining counter, not an ABI hazard: the v11 SDK's x86_64 library-call convention *is* r12 (2026-10-02)

- Source: ReIncarnation session, 2026-10-02 (opencode lane)
- Collected: 2026-10-02
- Published: 2026-10-02
- Prior: [2026-10-02-optimisation-level-alone-removes-every-xrun-on-the-dell.md](2026-10-02-optimisation-level-alone-removes-every-xrun-on-the-dell.md) (which raised `-O2` as the candidate answer), [2026-10-02-dell-sticky-log-location-and-size-heuristic-correction.md](2026-10-02-dell-sticky-log-location-and-size-heuristic-correction.md) (which promoted `r12moves` to "the discriminator")
- Commit: `7863e2b`. Source: SDK headers and build outputs, cited inline — `src/abi/v11/sdk/Developer/include/aros/x86_64/libcall.h` and its generator `src/abi/v11/AROS/arch/x86_64-all/include/gencall.c`; counts by `objdump -d` over `$OBJ/*.o` and the linked binary. Toolchain: `src/abi/v11/toolchain-core-x86_64`, GCC 16.1.0

## How this came up

The optimisation-level record said `-O2` was "not a free win: it doubles `r12moves`
(41 → 286)". That was reported as a caution, on the strength of a standing belief
that `r12moves` is an ABI safety signal. The lane was down, so this was checked
host-side — and the belief does not survive checking.

## The gate's stated invariant

`scripts/ri_audit.sh`, Phase 6:

> `-- ABIv1 LVO convention gate (2026-09-21 probe_ahi guest page-fault) --`
> `-- Guest binaries MUST emit rdx-base calls (build-pc SDK); any`
> `-- 'mov %rax,%r12' means the stale r12 SDK leaked in and the binary`
> `-- will fault on first LVO call. Checked on every AROS artifact. --`

and it fails any gated artifact whose count is non-zero. So the invariant is:
**zero `mov %rax,%r12`, ever.**

## What actually generates the instruction

`$SDK/include/aros/x86_64/libcall.h`, in the ABIv1 **v11** SDK the Dell build uses:

```c
#define AROS_LIBCALL_INIT(bn, o) \
    ... __asm__ __volatile__("movq %%r12, %0\n    movq %1, %%r12" : "=&rm"(__sto) : "rm"(_bn) : "r12");

#define AROS_LIBCALL_EXIT \
    __asm__ __volatile__("movq %0, %%r12 " : : "rm"(__sto) : "r12"); \
    __ret;
```

and every generated stub declares its base as a named register:

```c
register APTR __r __asm__("r12"); __asm__ __volatile__("":"=r"(__r):"0"(__r));
```

This header is autogenerated. `src/abi/v11/AROS/arch/x86_64-all/include/gencall.c`
emits exactly that text at lines 78, 104, 252, 256, 261 and 267. **The v11 x86_64
library-call ABI uses r12 as the base register by design**, and it saves and
restores r12 around every call, so r12 is preserved across it.

Three consequences, each checked rather than inferred:

1. **`-ffixed-r12` cannot suppress it.** The register is named in the asm template
   *and* in a `register ... __asm__("r12")` variable, so the compiler neither
   allocates nor rewrites it. Every CFLAGS line in this repo passes
   `-ffixed-r12`, believing it produces "zero `mov %rax,%r12`"; it cannot, and the
   build script's own comment saying so is wrong.
2. **There is no rdx variant to build against — and that is the error in this
   record, corrected below. Only v11 ships an arch-specific x86_64 header at
   all:**
   ```
   v11/core-pc-x86_64/bin/pc-x86_64/.../aros/x86_64/libcall.h   r12=45  rdx=0
   v11/core-pc-x86_64/bin/pc-x86_64/gen/.../aros/x86_64/libcall.h r12=45  rdx=0
   v1  -- no aros/x86_64/libcall.h exists --
   ```
   v1's x86_64 SDK provides `cpucontext.h` and `genmodule.h` instead. That is
   why a v1 build emits zero of these instructions and why the audit gate — which
   builds against the **v1** SDK and asserts zero — passes at zero.
3. **Therefore the count measures inlining, not ABI safety.**

## Why the count rises with optimisation

`r12moves` across the whole build:

| level | linked binary | **our own object files** |
|---|---|---|
| `-O0` | 41 | **0** |
| `-O1` | 307 | — |
| `-Os` | 138 | — |
| `-O2` | 286 | **245** |
| `-O3` | 324 | — |

At `-O0` the libcall stubs stay **out of line** and live in the prebuilt
libraries, so the asm is never inlined into our code and our objects contain
none. The 41 in the linked binary are all in SDK startup and libc —
`__startup_stdiowin` (9), `__startup_fromwb` (3), the libfunc boundary helpers
(`MUI_MakeObject`, `GetMsgFromStack`, `_set_open_libraries_list`, …) and libc
string/memory functions (`memcpy`, `strlen`, `memcmp`, …).

At `-O2` GCC inlines the header's stubs into our functions and drags the asm with
it. Confined to the eight files that actually call Amiga libraries:

```
73 riapp.o          57 audio_ahi_live.o   52 rsection.mcc.o   22 skin_aros.o
19 image_dt.o       17 fs_aros.o           3 pack_909.o         2 log_aros.o
```

**No engine or DSP object is affected at any level** — `engine.o`, `live.o`,
`rb303.o`, `rb808.o`, `rb909.o`, `levi*.o`, `fx.o`, `reverb.o`, `mixer.o` are all
zero. Two control experiments agree: a minimal probe compiles to 0 at `-O2` with
or without `-ffixed-r12` (no library calls), and `platform/pal/ri_pal_sticky.c`
also compiles to 0 standalone (no library calls) while the *linked* binary
attributes instances to that symbol.

## CORRECTION (2026-10-02, later the same day, found while starting `riqemu1`)

**This record's central claim was too strong and part of it was wrong. The gate's
premise is not "unachievable"; the gate is a v1-lane gate and it is coherent for
v1.** I read `find src/abi -name libcall.h` and concluded no rdx variant existed,
without noticing that the arch-specific header I was looking at belonged to **v11
only** and that v1 has no such header at all. The audit builds with
`V1SDK=src/abi/v1/core-pc-x86_64/...`, gates the artifacts it builds, and they
count zero — the gate works, on the lane it was written for.

What actually stands, and what does not:

- **Stands:** within the v11 lane the count is an **inlining counter**. `-O0` gives
  0 in our own objects and `-O2` gives 245, confined to the eight AROS-only files
  that call AHI/Intuition/dos, with no engine or DSP file affected. `-ffixed-r12`
  cannot suppress the v11 sequence because the register is named in the asm.
- **Stands, and is actually the *better* explanation:** `r12moves` is a reliable
  **ABI fingerprint** — it cleanly answers "which ABI did this build target",
  which is precisely how the size-heuristic record used it and why it worked for
  weeks. Zero means v1; a non-zero count means v11.
- **Wrong:** "the gate's stated invariant is unachievable in this tree", "an
  optimised build trips this gate for doing the wrong thing", and the framing that
  a v11 build is somehow non-conforming. The real and much narrower fact is that
  the v11-lane recipe `vms/ri-p9/build_v11.sh` lives **outside this repo**, so a
  v1-lane gate is never applied to its output. Two different ABIs, two different
  gates, and no contradiction between them.
- **Also wrong, and worth naming because I asserted it confidently:** I wrote that
  `r12moves` "must stop being cited as evidence of ABI conformance". It is evidence
  of ABI *identity* — v1 versus v11 — which is a stronger and more useful claim
  than the one I replaced it with.

**The error was mine, it shipped, and it was found by going to look rather than by
re-reading my own reasoning.** Nothing prompted this except needing to build a
binary for a *different lane* (`riqemu1`, the ABI v1 VM) and asking which SDK the
recipe used. `ri_build_aros.sh` defaults to `V1SDK=.../abi/v1/...`; that one line
would have answered it at the start.

**And the wiki already had the answer.** The 2026-09-23 record
[riqemu1/Dell GUI first light](../articles/2026-09-23-dell-gui-first-light-classic-window.md)
says, in a parenthetical, *"note the inversion: r12 moves EXPECTED here, the r12==0
gate is v1-guest-only"*. That is precisely the right reading, written three months
earlier, and it was not opened before a same-day record asserted the opposite. **The
error was available to catch from inside this wiki and was not caught from inside it.**
The same day then corrected it a second time when a *different* record realised r12
is AROS's documented ABI — so this record's claim survived one round of self-review
and needed a second. What would have prevented both is the thing the wiki exists to
provide: read the lane's own prior records before asserting something about it.

The method lesson is the sharpest thing in this record now: **a conclusion drawn
from a search needs the search's scope stated.** "There is no rdx libcall.h" was
true and useless; "there is no rdx libcall.h *in v11*, and v1 has no arch-specific
header at all" is the fact, and it inverts the verdict. When a finding says a
*rule* is wrong, check which lane the rule is written for before declaring it
broken.

## What this does and does not settle

**Settles:** `r12moves` is not an ABI hazard signal. It is very nearly a measure
of "how much did the compiler inline", which is why it separated the v1 and v11
builds and why it tracks the optimisation level so closely. The
[size-heuristic record](2026-10-02-dell-sticky-log-location-and-size-heuristic-correction.md)
was right that size cannot separate the lanes and promoted `r12moves` as the
discriminator; it is still a good *build fingerprint*, but it must not be cited as
evidence of ABI conformance.

**Does not settle:** the 2026-09-21 `probe_ahi` page fault was real. Since the v11
SDK **is** an r12 SDK, that fault's attribution — "the stale r12 SDK leaked in" —
needs re-examination, and it cannot be settled from the source tree. Two complete
`-O2` sessions on the Dell (0 xruns each, `render_max` 3028/3039 µs, with
continuous AHI and Intuition calls) are consistent with the trampoline being safe
and are not proof of it. The `-O2` decision is therefore blocked on **understanding
the v11 LVO convention**, not on more performance measurement — which is a much
more tractable question than the one it replaces.

## What was deliberately not done

The gate's pass/fail logic is **unchanged**. Relaxing a gate written after a real
fault is an owner decision, and the finding above does not identify the fault, so
it does not entitle anyone to remove the check. Only the comment was corrected,
in place, with the evidence and the "why this is still failing for the wrong
reason" note. `AUDIT 0/0 PASS` still holds, because the gated artifacts are
`probe_ahi` and `reincarnation_stub.library`, which make no library calls and
legitimately count 0.

## Method findings

- **A metric promoted to "discriminator" can be measuring the wrong quantity
  entirely, and it will keep working.** `r12moves` cleanly separated every build
  in this lane for weeks, which is exactly why nobody asked what it counted. A
  metric that correlates perfectly with the thing you want is not thereby
  measuring the thing you want.
- **Check the generator, not the generated file.** The header says r12; the file
  that produces it says r12 on purpose. One grep of `gencall.c` settled a question
  that three rounds of disassembly had only narrowed.
- **`-ffixed-r12` is a compiler-allocation constraint and cannot override an asm
  template.** It appears in every CFLAGS line here as if it were an ABI switch.
  It is not, and believing it was is what made the count look like a bug.
- **A caution carried forward unexamined becomes a blocker.** "-O2 doubles
  r12moves" was written as due caution and then inherited as settled. It took a
  dead lane and an idle afternoon to notice it had never been checked, which is
  an argument for checking cautions at the moment they are written rather than
  when they start to matter.
- **Per-object counts beat per-symbol counts in a linked binary.** Attributing
  `mov %rax,%r12` to symbols by nearest-preceding-label put instances in a file
  that compiles to zero; counting in the `.o` files gave the true distribution and
  immediately showed the eight-file shape.

## Standing gaps

- The actual cause of the 2026-09-21 `probe_ahi` page fault. Until it is known,
  the gate cannot be made precise rather than merely relaxed, and `-O2` cannot be
  declared safe.
- Whether the r12 trampoline is safe in every path, particularly around
  interrupts and inside the priority-21 audio task — the one place where a
  clobbered base register would be hardest to notice.
- No `-O` level avoids it: `-O1` 307, `-Os` 138, `-O3` 324. The choice is binary,
  `-O0` or not-`-O0`.
- The section-level render split still has no device measurement; the lane is
  down.
