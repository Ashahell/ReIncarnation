# F1: MEMTYPE — Dell VESA framebuffer is UC (MTRR default, PAT[0]=WB)

Date: 2026-10-07. Probe: `lane/memtype/` (`memtype.c`, `memtype_decode.*`,
`suptest6.c`, `build.sh`). Decoders pinned by `tests/unit/t177_memtype_decode.c`
(GF1a: PASS, PCD/PWT-swap mutant FAILs — see commit `97dbd04`).

## Method (read-only)

- Privileged reads run inside `SuperState()`/`UserState()` windows (CPL 0):
  direct `RDMSR` / `MOV`-from-`CR3` via integer-only inline asm. No `WRMSR`,
  no CR writes, no page-table writes.
- Every `RDMSR` gated on its CPUID bit; variable MTRRs read only for
  n < VCNT (window 1 reads MTRRCAP/DEF_TYPE first, window 2 the rest);
  fixed MTRRs read only when FIX=1.
- Builds: ABIv11 `MEMTYPE.v11` (Dell) and ABIv1 `MEMTYPE.v1` (QEMU) from the
  same source; both links check 0 unresolved (`build.sh`); v1 additionally
  checks 0 r12 moves. Stdout redirected to `RAM:` on-target and `--get`'d.
- Mechanism note: the first design (one `Supervisor()` call per MSR with an
  `iret`-terminated worker) hangs on riqemu1 — every binary calling
  `Supervisor()` wedged the exec with no output and eventually dropped the
  guest agent (4 cycles, 2 guest reboots; kernel entry/exit quad counts
  verified statically, handler registered — cause not pursued). `SuperState()`
  on the same guest reads MTRRCAP and CR3 cleanly (`suptest6.c`), so the
  probe does everything inside SuperState windows. `int $0xFE` itself works;
  the `core_Supervisor` jmp-to-worker return path is what never comes back.
- `startup.o` leaves `DOSBase` NULL: the first `Printf` through it faults.
  Every probe does the manual `OpenLibrary("dos.library")` open/close, same
  shape as `audio_io/probe_ahi.c` (which is why probe_ahi always worked).

## Decode reasoning (Dell)

- Source: bootloader VESA info (`0xD0000000`, 67043328 B) — the driver path
  of F0 Q1, so this is the range `UpdateRect` writes.
- MTRR: E=1 (enabled). Valid ranges cover RAM as WB up to `0xCC000000`
  (MTRR0–3), one UC carve-out (MTRR4), RAM above 4 GiB (MTRR5–7). The FB
  range `[0xD0000000, 0xD3FEFFFF]` matches none of them (nearest: MTRR2 ends
  `0xC8000000`; next range starts at `0x100000000`) → **default type**, which
  is **UC**. MTRR8 (V=0, stale WC entry) correctly ignored; MTRR9 unused.
  All three sample points agree.
- PAT: index 0 at base, mid and last byte (2 MiB pages, PWT=0 PCD=0
  PAT12=0 at every level — as F0 Q2 predicts) → PA0 = WB (power-on PAT
  confirmed byte-exact).
- Effective (§0.3 row WB+UC→UC): **UC**.

## Answer

`FB effective=UC via MTRR=UC(default) PAT[0]=WB`. The BIOS covers RAM with
WB and leaves the PCI hole at the UC default; AROS programs neither MTRRs
nor PAT (F0 Q3), and v11 `MapPCI` adds no caching attribute (F0 Q1). The
framebuffer the VESA driver writes is uncached — as inferred, now proven.

`RAM:` cleaned on the Dell (`list RAM:` shows agent files only). No disk,
ENVARC or boot writes; nothing scoring F3 ran. riqemu1 left running + idle
(owner-loaned; agent session 4).
