## The patch (HDAudio)

`workbench/devs/AHI/Drivers/HDAudio/main.c`, `_AHIsub_AllocAudio`, after
the CANRECORD loop — one added statement:

```c
/* Report the rate the hardware will actually run. The converter and
   stream formats are programmed from selected_freq_index, not from
   the request, so without this the mixer runs the request while the
   hardware runs the nearest listed rate and nothing reports it. */
AudioCtrl->ahiac_MixFreq = card->frequencies[card->selected_freq_index].frequency;
```

- The existing below-floor clamp (`main.c:107-108`) is kept: redundant but
  harmless, and it keeps the diff to one statement.
- The CANRECORD loop (`main.c:127-134`) still sees the original request,
  so record capability stays conditional on the request being exact —
  zero behavior change there. (Alternative considered: capture exactness
  first and re-check after; rejected — placing the write-back after the
  loop achieves the same with a pure addition.)
- Same one-liner in `Drivers/NVHDMI/main.c` (identical defect shape; the
  converter is programmed from `selected_freq_index` in `hdmi.c:672`).

## Core analysis (`Device/audioctrl.c`): no core hunk, and why

Checked every value derived from the requested `ahiac_MixFreq`:

| value | where computed | relative to `AHIsub_AllocAudio` | stale after write-back? |
|---|---|---|---|
| `ahiac_AntiClickSamples` | `CreateAudioCtrl` (`audioctrl.c`, from `AHIA_AntiClickSamples` default `AntiClickTime * MixFreq >> 16`) | before | **yes, only this one** |
| `ahiac_Min/MaxBuffSamples` | `UpdateAudioCtrl` (`audioctrl.c:518`), called after `AHIsub_AllocAudio` returns (`:511`) | after | no |
| `ahiac_BuffSamples`/mix buffer | `RecalcBuff` during post-alloc setup | after | no |

So the "trap" is half-real: the buffer sizing the plan worried about
(`MaxBuffSamples` too small for the true rate) is computed **after** the
driver call and picks the written-back rate up. The one genuinely stale
value is the anti-click fade length, off by request/selected (typically
±4 %, pathological ≤ ~4× for absurd requests) — inaudible, and the Toccata
precedent (`toccata.c:235`, writing back since forever) already exercises
this exact path harmlessly. A core hunk re-deriving one fade length is
review risk for no audible gain: **no core change; stated here instead.**
